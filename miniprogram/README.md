# CityWalk Planner WeChat Mini Program

这个目录用于承载微信小程序端功能，和现有 Web 管理端保持同一个业务域，但代码独立。

## 功能目标

现有 Web 端负责手动规划和管理路线；小程序端负责在移动场景中查看已有路线，并把用户实际走过的轨迹直接保存成新的规划路线。

第一阶段建议做成两个核心能力：

1. 路线查看
   - 拉取现有 `/api/tree` 数据。
   - 在地图上显示所有可见路线。
   - 支持选择某条路线并聚焦到该路线。
   - 保留路线颜色、名称、描述和点位顺序。

2. 实际轨迹记录
   - 用户点击开始记录后，请求定位权限。
   - 监听位置变化，并将用户走过的位置实时绘制为一条 polyline。
   - 定位点只保存在小程序内存状态里，作为临时路线草稿。
   - 用户点击结束记录后，输入路线名称和描述。
   - 用户确认后，直接把临时点位保存为一条新的 route plan。

## 和现有系统的关系

现有 route plan 数据可以继续作为“计划路线”：

```ts
type RoutePlan = {
  id: string;
  name: string;
  color: string;
  isVisible: boolean;
  points: { lng: number; lat: number }[];
}
```

小程序不新增数据库表。walk 过程中的点位只是临时状态，确认保存时写入 `route_plans.pointsJson`。

## 坐标系统

这是这个功能里最容易踩坑的地方。

- Web 端使用百度地图，现有路线点通常是 BD-09 坐标。
- 微信小程序地图和定位常用 GCJ-02 坐标。
- 小程序展示现有路线时，需要把 BD-09 转成 GCJ-02。
- 小程序实时画线时使用 GCJ-02 原始定位点。
- 小程序保存为 route plan 前，把 GCJ-02 转成 BD-09，保证 Web 百度地图展示不偏移。

当前目录里已经提供 `utils/coord.js`：

- BD-09 -> GCJ-02：小程序展示已有路线。
- GCJ-02 -> BD-09：小程序保存实际 walk 为新路线。

## 建议后端增量

第一阶段需要新增这些 API：

- `GET /api/tree`：复用现有接口，供小程序读取路线。
- `POST /api/routes/from-walk`：用户结束 walk 并确认后，直接创建新的规划路线。

后续可以追加：

- 服务端或小程序端追加轨迹抽稀，减少点数。

## 小程序端页面规划

第一版先只放一个地图主页面：

- `pages/map/index`
  - 地图显示
  - 路线 polyline
  - 实时轨迹 polyline
  - 开始/暂停/结束记录
  - 聚焦当前位置

第二阶段再拆：

- `pages/routes/index`：路线列表和筛选。

## 开发注意

- 真机测试定位和后台定位，小程序开发者工具的模拟定位不足以验证完整体验。
- 生产环境接口必须使用 HTTPS，并配置到微信小程序后台合法域名。
- 持续定位和后台定位需要在 `app.json` 中声明权限说明，并按微信审核要求解释用途。
- 后台定位需要用户授权“使用小程序期间和离开小程序后”。如果后台定位开启失败，小程序会自动降级为前台定位。
- 轨迹点需要节流和抽稀，不能把每一次定位变化都无条件保存到数据库。
